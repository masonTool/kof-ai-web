# 角色动作专属化 · 规划与进度

> 目标：让**每个角色的招式有各自的动作**，而不是所有角色共用一套姿势。
> 进度以本文件的表格为准，每完成一个角色就更新一次。

## 一、现状（这是个真问题）

所有角色共用**同一套 33 个动画**，只有外观（发型/服装/配色）不同：

```js
// scripts/sprites/chars.mjs —— 每个角色只有"长什么样"
kyo: { name: '草薙京', look: '黑色刺猬头碎发…白色高立领学生服…' }

// scripts/sprites/gen-poses.mjs —— 动作描述是**全局通用**的
specialprojectile: '波动系必杀：双脚前后站稳、双手从腰侧向前推出…'
```

出图时把两者拼起来：「参照这张图的角色形象 + 姿态：${通用动作描述}」。

**结果**：京的「荒咬」、八神的「屑風」、Terry 的「Power Wave」、Athena 的「Psycho Ball」
——四个完全不同的招，用的是**同一个"双手前推"姿势**。

对照实际的招式名：

| 角色 | 236 系必杀 | 现在用的姿势 | 应该是什么动作 |
|---|---|---|---|
| 草薙京 | 百拾四式・荒咬 | 双手前推 | 上半身带火焰的拳击 |
| 八神庵 | 屑風 | 双手前推 | 单手抓扯、把对手甩出去 |
| Terry | パワーウェイブ | 双手前推 | 单手挥地、打出一道地面波 |
| Athena | サイコボール | 双手前推 | 双手在胸前搓出能量球 |

## 二、已经具备的条件

**数据层不用改**：招式本来就可以指定独立的动画名。

```ts
mv('236A', '百拾四式・荒咬', 'punchLight', 26, 'special', [...])
//                          ^^^^^^^^^^^^ 这个字段就是动画名
```

所以要做的事只有两件：**出图** + **把 anim 名填成专属的**。

## 三、做法（每角色 3 步）

1. **写专属提示词**：按该角色的招式名写姿态描述
   （例：`kyoSpecial236 = '上半身前压、右手成爪向前上方撩出、腕部有橙色火焰缠绕'`）
2. **出图**：每个必杀 3 帧（起手 / 出手 / 收招），每角色 4 个必杀 = 12 张
3. **配置**：`build-sheet.mjs` 加动画、`poses.ts` 加程序化兜底、
   角色数据里把 `mv()` 的第 3 参数改成专属名

## 四、成本

| 项 | 数量 |
|---|---|
| 每个角色 | 4 个必杀 × 3 帧 = **12 张图** |
| 27 个角色 | **324 张图** |
| 出图耗时 | 每张约 30 秒 + 限流间隔 → **每角色约 11 分钟，全部约 5 小时** |

### 基础设施：`exclusive` 标记（本批修）

之前 `art:check` 用**正则猜名字前缀**来排除专属姿势，每专属化一个角色都要手改，
漏一次就误报 26 条「缺动画」——**已经踩了三次**（京→八神→Terry/Athena→红丸/大门）。

现在改成在姿势上**自声明**：

```ts
benispecial1: {
  frameDuration: 1,
  loop: false,
  frames: [...],
  exclusive: 'benimaru',   // ← 只有这个角色有，别要求全员
}
```

`poseNames()` / `exclusivePoseNames()` / `check-assets.mjs` / 测试全部改成读这个字段。
**以后加角色只需在姿势里写一行 `exclusive`，不用再动校验脚本。**

## 六点五、起手帧补齐（完成）

原先 107 个专属动作**各只有 1 帧**（出手瞬间），放招是"突然切换"。现已全部补成 **2 帧**：

```
['<招式>windup', '<招式>']   →   起手收势  →  出手爆发
```

**做法（批量派生）**：从每个出手提示词里提取「角色名 + 招式名」，套统一模板生成起手提示词：

> `<角色>「<招式>」的起手瞬间：身体重心下沉、动作收在起始位置蓄力、气息开始在掌心汇聚、还没完全展开`

**先试过一版更"聪明"的**：把原提示词里的特效描述（`**...**`）塞进起手句，结果出来是
「紫红色火焰贴地向前窜出刚开始在周身汇聚」这种语法不通的描述。**收势姿态交给 AI 自己发挥，只给"蓄力"这一个约束，反而更准。**

**结果**：115 个起手帧全部出图，27 个角色全量重打包失败 0。

## 六点六、收招帧补齐（完成）

107 个专属动作从 **2 帧**扩到 **3 帧**：

```
起手（蓄力）→ 出手（爆发）→ 收招（收回）
```

**同样的批量派生法**：`<角色>「<招式>」的收招瞬间：动作打完开始收回、气息逐渐消散、身体回到站立的姿态、还没完全放松`

**这次改 `poses.ts` 用了逐行/逐块处理**（不再用跨行正则）：
之前两次跨行正则把 84 个块合并成一个、还扩出过 255 帧，是这轮最大的教训。
处理后用 `npx tsx` 直读 `POSE_LIBRARY` 验证「107 个全是 3 帧」才算完。

**结果**：111 个收招帧出图、27 角色全量重打包失败 0、**997 条测试全绿**。

### 正常技专属化的一个坑

`terry`/`andy` 这类用 `buildNormals()` 批量生成普通技的角色，**重攻击的动画名是硬编码的**
（`HEAVY_ANIM = { punch: 'punchHeavy', kick: 'kickHeavy' }`），`style.anim` 改不了。

已在 `template.ts` 里扩展：`NormalStyle.anim` 支持 `heavyPunch`/`heavyKick`，
`buildNormals` 内部优先用它们。以后这类角色直接传参即可：

```ts
...buildNormals({ power: 1.02, cancels: CANCELS, anim: { heavyPunch: 'terryheavypunch', heavyKick: 'terryheavykick' } })
```

## 六点十六、挥空音效（`whiff` 从"定义了但从不触发"变成真音的）

**盘点方法**：把 `SFX` 表里的 27 个音效名逐个反查引用（这次**不排除任何文件**，包括
`sfx.ts` 自己的 `return 'xxx'`），结果只有 **1 个**从未被引用：`whiff`。

**为什么它从没响过**：音效表里有 `whiff` 定义，但模拟层**从来没有抛出过 `whiff` 事件**——
打空和打中在音效上完全一样。

**补齐的三处**：
1. `Fighter` 加 `moveLanded`（本招是否命中过）与 `moveWhiffed`（刚挥空结束，供消费）
2. 招式自然结束处（`moveFrame >= total`）：`if (!moveLanded) moveWhiffed = true`
3. `Match.step` 消费它并 `emit('whiff', …)`；`sfxForWorldEvent` 加 `case 'whiff'`

**为什么用"置标志 + Match 消费"**：`Fighter` 没有 `world` 引用（事件都在 `Match` 层发），
硬塞一个引用会破坏现有的分层。

## 六点十七、有利帧显示

之前没做的原因：算有利帧需要"对手还剩几帧硬直"，而 `Fighter` 只暴露了**递增的**
`stateFrame`（已经过了几帧），算不出剩余。

**补的字段**：`Fighter.stunTotal`——`enterHitstun()` 时记一次总量。有了它就能算：

```
我的剩余收招 = move.total - moveFrame
对手剩余硬直 = stunTotal - stateFrame
有利帧       = 对手剩余硬直 - 我的剩余收招   （>0 我占优）
```

只在「我在出招 + 对手在硬直」时显示，否则不出现（避免面板一直占着一行）。

**判断"还在硬直中"用的是 `stateFrame < stunTotal`**——不是比状态名：硬直结束后
`stateFrame` 会继续涨、超过 `stunTotal`，这个条件自然失效，不用额外记标志。

## 六点十八、回滚骨架（线上对战的第一块基石）

**不是快照，是"重放输入"**。`World.entities` 里存着 `p1`/`p2` 的**引用**，
`structuredClone` 出来是纯对象，`Object.assign` 回填会把这些引用和 Fighter 的方法一起弄丢。

**方案**（`src/net/rollback.ts`）：

```ts
class RollbackSession {
  step(inputs)                    // 记录输入 + 推进
  rewindTo(frame, replacement)    // 截断 → 拼接新输入 → 重建 Match → 重放
  verifyDeterministic()           // 从头重放，比对 hash
}
```

**成本**：一次回滚 = 重建 Match + 重放 N 帧（N 通常 2~7，等于延迟帧数）。
60fps 预算 16.6ms，重放 7 帧完全够。

**已验证的四件事**：
1. 从头重放得到的 hash 与当前状态一致（**模拟层是自洽的**，这是回滚的前提）
2. 回滚并替换输入后，状态与"直接这么打"完全一致
3. 帧号越界会明确报错（不静默）
4. 回滚到当前帧（替换为空）等于什么都不做

**还没做的**：输入传输（WebRTC/WebSocket）、延迟补偿、对手输入预测。
这些都在 `RollbackSession` 之上——只要"重放一定得到同一状态"这一层站得住，上面就好搭。


## 六点十九、资源体积优化（302MB → 157MB，-48%，无损）

**问题**：`public/sheets` 302MB，单角色最多 8.5MB（chang 的扩展片单张 13MB），
首屏/进对局加载很慢。

**先量再改**，测出来的数据决定了方案：

| 指标 | 实测 |
|---|---|
| 图集总数 | 58 张（29 角色 × 2 片） |
| 总像素 | **1904M** |
| 装箱利用率 | **89.5%**（已经不浪费，问题在像素总量本身） |
| 最大图集 | 2048×29739 |
| 单图颜色数 | 31 色（已量化） |

**试过但无效/不可行的**：
- **PNG-8 索引色**：只有 31 色，但 (RGB,A) 组合有 **1586 种**（alpha 是 31 级阶梯），超过 256 色上限
- **PNG Paeth filter**：对低色数量化图**反而变大 62%**（filter 0 才是最优）
- **降 RES 8→6**：能再减 44% 像素，但大窗口/高分屏会糊，用户要求不动画质 → 不采用

**最终方案（严格无损）**：
1. **画布 2048 → 4096 宽**：高度从 29000 降到约 14000，**先解决 WebP 的 16383 单边上限**；
   宽图连续像素更多，压缩率也更好（顺带 PNG 就小了约 20%）
2. **PNG → WebP 无损**（`cwebp -lossless -z 6`），逐字节比对 **0 差异**
3. **没有 cwebp 的环境自动保留 PNG**（加载器读 json 的 `image` 字段，两条路都能跑）

**结果**：302MB → **157MB（-48%）**；最大单张 13MB → 5.6MB（-57%）。

**改到的文件**：
- `build-sheet.mjs`：`MAX_W` 默认 4096（可用 `SHEET_MAX_W` 覆盖）、`toWebpOrKeep()`、`readSheetImage()`（派生变体时能读 WebP 源）
- `check-assets.mjs`：`sheetPath()`（.png/.webp 都认）、`imageSize()`（读 WebP 头不解整图）、`decodeAny()`
- `.gitignore`：`!public/sheets/*.webp`
- `tests/variants.test.ts`：图集扩展名不再锁死 `.png`

**遗留**：`benimaru-extra` 在 4096 宽下仍有 16952 高（超限），单独用 `SHEET_MAX_W=8192` 重打成 8192×8828 后转 WebP 成功。
